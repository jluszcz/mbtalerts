# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

mbtalerts fetches active MBTA subway alerts (Red, Orange, Blue, Green) from the
[MBTA v3 API](https://api-v3.mbta.com) and either prints them to the terminal or syncs them to Google Calendar. Titles
are generated by AWS Bedrock when credentials are available and derived from the alert header otherwise.

## Architecture

- **`src/lib.rs`** — `alerts()` (fetch + daily cache), the `Line` enum and `canonical_line`/`line_name` route
  canonicalization, and `should_sync_alert` (station-level noise filter)
- **`src/summary.rs`** — title generation: `event_summary` (deterministic fallback) and `generate_or_fallback` (Bedrock
  with fallback), plus the header-parsing helpers
- **`src/calendar.rs`** — Google Calendar client, alert→calendar routing, and the create/update/delete sync planner
- **`src/ai.rs`** — `BedrockSummarizer`
- **`src/main.rs`** — CLI; **`src/lambda.rs`** — AWS Lambda entry point. Both share `alerts()`, `CalendarClient`, and
  `sync_alerts`
- **`src/types.rs`** — API types and `Alert::builder()`
- **`mbtalerts.tf`** — Lambda, IAM, and the EventBridge schedule

## Conventions

### Bedrock is optional, always

`BedrockSummarizer::from_env()` returns `None` when AWS credentials are absent (`src/ai.rs`). The CLI routinely runs
without them; the Lambda is always credentialed. **Every path must degrade to `summary::event_summary`.**

`generate_or_fallback` returns `AlertSummary { raw, display }`, where **`raw.is_some()` is the signal that the AI
produced the title**. Branch on that — never re-derive intent from `uses_first_sentence_summary`, which describes what
the *fallback* summarizer would have done. Getting this wrong silently drops content (see `alert_body` in
`src/main.rs`).

### Calendar sync protocol

Events are identified and diffed purely through Google `extendedProperties.private` keys:

| Key | Purpose |
|---|---|
| `mbta_alert_source=true` | Filters the list request to events this app owns |
| `mbta_alert_id` | Maps an event back to its alert |
| `mbta_ai_summary` | The AI-generated title, when there was one |
| `mbta_alert_state_hash` | `event_state_hash` of the alert the event was written from |

**Renaming any of these orphans every existing event**, and the next sync deletes and recreates the entire calendar.

`event_state_hash` must cover everything the rendered event depends on — currently header, description, url, active
period bounds, effect, and the sorted routes. Adding a field to the title or the routing means adding it to the hash;
otherwise that change never re-syncs. Widening the hash invalidates every stored hash, so the first sync afterwards
rewrites every event once.

`mbta_alert_state_hash` is always written, even with no AI summary. `plan_calendar_sync` takes an `AiSummaries` flag so
it only demands an `mbta_ai_summary` when a summarizer actually exists — otherwise an uncredentialed run rewrites every
event on every pass, forever.

### Testing

Tests are pure: no HTTP mocking, no network, no AWS. Keep it that way — factor new logic into pure functions (see
`plan_calendar_sync`) so it stays testable. `Alert::builder()` (`src/types.rs`) is the fixture constructor and lives in
production code deliberately. `tests/fixtures/alerts.json` is a captured API response, `include_str!`'d into the
library and used for both the deserialization test and property assertions over real header shapes.

One papercut: the fixture is a single line with no trailing newline, so `pre-commit run --all-files` "fixes" it and
produces a ~380 KB one-line diff. The commit hooks only see staged files, so this bites only when running the hooks
manually — discard that change rather than committing it.

## Development Commands

- `cargo build` - Build
- `cargo test` - Run all tests
- `cargo fmt` / `cargo fmt --check` - Format / check formatting
- `cargo clippy --all-targets -- -D warnings` - Lint (CI denies warnings)
- `pre-commit run --all-files` - Run the configured hooks

CI runs on `ubuntu-24.04-arm` against `aarch64-unknown-linux-musl` via `jluszcz/github-utils` reusable workflows; to
reproduce a CI-only failure, append `--target aarch64-unknown-linux-musl`.

## Environment Variables

| Variable | Description |
|----------|-------------|
| `GOOGLE_SERVICE_ACCOUNT_KEY` | Service account key JSON (required for calendar sync) |
| `GOOGLE_CALENDAR_ID` | Single target calendar. Used when `GOOGLE_CALENDAR_IDS` is unset |
| `GOOGLE_CALENDAR_IDS` | JSON mapping line names to calendar IDs; requires a `default` key. Takes precedence |
| `BEDROCK_MODEL_ID` | Bedrock model for AI titles. Defaults to `us.amazon.nova-2-lite-v1:0` |

## Deployment

`mbtalerts.tf` provisions the Lambda, which EventBridge invokes on a `rate(3 hours)` schedule. On a push to `main`, CI
packages the `lambda` binary and uploads `mbtalerts.zip` to the us-east-2 code bucket — it does **not** call
`update-function-code`; the LambdUpdate watcher picks the object up and updates the function. Terraform is **not** run
by CI.

The Bedrock IAM policy pins both the foundation model and inference profile ARNs (`mbtalerts.tf:75-80`), so changing
`BEDROCK_MODEL_ID` requires a matching Terraform change and apply.
